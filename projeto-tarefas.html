PHP Projeto Tarefas com SQLite

A Ana vive esquecendo coisas. Neste projeto você faz para ela uma lista de tarefas que fica guardada num banco de dados: ela adiciona, marca como feita, corrige e apaga. Essas quatro operações têm um nome famoso, CRUD (Create, Read, Update, Delete: criar, ler, atualizar, apagar), e estão por trás de quase todo sistema: loja, blog, agenda, rede social. Quem faz um CRUD bem feito sabe fazer os outros.

Você vai aprender
  • Criar o banco SQLite e a tabela a partir do PHP, com PDO.
  • R: ler as linhas com query + fetchAll e mostrar numa lista.
  • C: inserir com prepare + execute e voltar para a lista (Post/Redirect/Get).
  • U: marcar como feita e editar o título com UPDATE … WHERE id = ?.
  • D: excluir com DELETE … WHERE id = ?.
  • Ver uma injeção de SQL apagar a tabela inteira, e o prepared statement impedir o mesmo ataque.

O projeto tem dois arquivos: banco.php (a conexão) e index.php (a página, que faz tudo). Uma página só, com um campo escondido acao em cada formulário dizendo o que fazer, mantém o projeto pequeno e fácil de seguir.

O sqlite3 que aparece em alguns comandos é o programa de terminal do SQLite, para espiar o banco por fora do PHP (no Debian/Ubuntu: sudo apt install sqlite3). Ele é opcional: tudo funciona sem ele.

    WHERE id = ?Só a tarefa daquele id. Um UPDATE sem WHERE muda todas as linhas da tabela.

  7. Etapa 7 · A prova: injeção de SQL

    Todos os SQL com valores de fora usaram prepare + execute. Para ver o que isso evita, troque (só para testar!) o excluir pela versão "ingênua", que cola o valor no texto do SQL:

        if ($acao === 'excluir') {
        $pdo->exec('DELETE FROM tarefas WHERE id = ' . $_POST['id']); // ERRADO!
        voltar();
    }

    Com um id normal, funciona igual. Agora, com o banco recém-criado (3 tarefas), dois envios "estranhos":

    $ curl -s localhost:8000/ | grep pendente
<p>2 pendente(s) de 3 tarefa(s).</p>
$ curl -s -d 'acao=excluir&id=abc' localhost:8000/ | head -8
<br />
<b>Fatal error</b>:  Uncaught PDOException: SQLSTATE[HY000]: General error: 1 no such column: abc in /home/ana/tarefas/index.php:53
Stack trace:
#0 /home/ana/tarefas/index.php(53): PDO-&gt;exec('DELETE FROM tar...')
#1 {main}
  thrown in <b>/home/ana/tarefas/index.php</b> on line <b>53</b><br />
$ curl -sL -d 'acao=excluir&id=0 OR 1=1' localhost:8000/ | grep -E 'pendente|class="tarefa"'
<p>0 pendente(s) de 0 tarefa(s).</p>          « TODAS as tarefas sumiram
$ sqlite3 tarefas.sqlite 'SELECT COUNT(*) FROM tarefas'
0

    O que aconteceu: o SQL montado foi DELETE FROM tarefas WHERE id = 0 OR 1=1. "id é 0 ou 1 é igual a 1" é verdade para toda linha, e o banco apagou tudo. No primeiro envio, abc virou o nome de uma coluna que não existe (no such column: abc): o texto do usuário foi lido como parte do comando. Isso é a injeção de SQL, um dos ataques mais antigos e mais comuns da web.

    A mesma tentativa contra a versão correta, também com o banco recém-criado:

    $ curl -sL -d 'acao=excluir&id=0 OR 1=1' localhost:8000/ | grep -E 'pendente|class="tarefa"'
<p>2 pendente(s) de 3 tarefa(s).</p>
    <span class="tarefa">Comprar pão</span>
    <span class="tarefa">Pagar a conta de luz</span>
    <span class="tarefa"><s>Estudar PHP</s></span>
$ sqlite3 tarefas.sqlite 'SELECT COUNT(*) FROM tarefas'
3

    Nada apagado: com o prepared statement, 0 OR 1=1 é só um valor procurado na coluna id (e o (int) ainda o reduz a 0), nunca um pedaço de SQL. A regra, sem exceção: valor que vem de fora entra no SQL só por ?. Mais em Prepared Statements e SQL Injection.

Quando dá errado

Fatal error: Uncaught PDOException: SQLSTATE[HY000]: General error: 1 no such column: …

O SQL fala de uma coluna que a tabela não tem. Pode ser um erro de digitação (titlo), uma coluna que você acrescentou ao CREATE TABLE depois de o banco já existir (o IF NOT EXISTS não altera tabelas existentes: apague o tarefas.sqlite para recomeçar, ou use ALTER TABLE), ou, como na etapa 7, um valor colado no SQL.

SQLSTATE[HY000]: General error: 1 no such table: tarefas

O PHP abriu um arquivo de banco diferente do que você imagina, um arquivo novo e vazio. Acontece com caminhos relativos (new PDO('sqlite:tarefas.sqlite')), que dependem da pasta de onde o PHP foi chamado. Use sempre __DIR__ . '/tarefas.sqlite'.

SQLSTATE[HY000]: General error: 8 attempt to write a readonly database

O PHP consegue ler o arquivo, mas não escrever. Num servidor, o usuário do PHP (www-data) precisa de permissão de escrita no arquivo e na pasta (o SQLite cria arquivos temporários ao lado).

A lista não muda depois de clicar, ou muda duas vezes com F5

Faltou o voltar() (Post/Redirect/Get) depois de gravar, ou o exit dentro dele. Confira no terminal do servidor: cada clique deve aparecer como [303]: POST / seguido de [200]: GET /index.php.

Resumo

  • new PDO('sqlite:' . __DIR__ . '/arquivo.sqlite') + CREATE TABLE IF NOT EXISTS deixam o banco pronto, sem instalar servidor.
  • CRUD: INSERT (criar), SELECT (ler), UPDATE (atualizar), DELETE (apagar).
  • Valor que vem de fora: sempre prepare com ? + execute([...]). SQL fixo pode usar query/exec.
  • UPDATE e DELETE sempre com WHERE (a não ser que você queira mesmo mexer em todas as linhas).
  • Ações que mudam dados: formulário POST + Post/Redirect/Get. Ler (como abrir a edição) pode ser GET.
  • O banco guarda o texto como veio; a página escapa na hora de mostrar.
