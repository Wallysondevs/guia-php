PHP Padrões PSR

Cada programador tem as suas manias: chaves na mesma linha ou na de baixo, calcular_total ou calcularTotal, tab ou espaços. E cada biblioteca tinha o seu jeito de registrar logs, de carregar classes, de representar uma requisição HTTP. As PSRs são acordos da comunidade PHP para que todo mundo escreva do mesmo jeito e para que bibliotecas diferentes se encaixem como peças de LEGO.

Você vai aprender
  • O que é uma PSR e quem é o PHP-FIG.
  • As regras de estilo: PSR-1 (o básico) e PSR-12 (a formatação), e o sucessor PER Coding Style.
  • A PSR-4 (autoload), em uma frase.
  • A PSR-3: uma interface de log que todas as bibliotecas entendem.
  • A ideia da PSR-7 e da PSR-15 (requisições HTTP e middlewares).
  • Ferramentas que conferem e consertam o estilo: PHP_CodeSniffer e PHP-CS-Fixer.

A ideia: tomadas padronizadas

Qualquer aparelho comprado no Brasil encaixa em qualquer tomada brasileira, porque fabricantes concordaram com um padrão. Ninguém é obrigado por lei da física a seguir o padrão, mas quem não segue fica sem clientes.

As PSRs são isso para o PHP. PSR quer dizer PHP Standards Recommendation, "Recomendação de Padrão do PHP". São documentos numerados (PSR-1, PSR-3, PSR-4…) escritos pelo PHP-FIG (PHP Framework Interop Group, "Grupo de Interoperabilidade de Frameworks PHP"), um grupo formado em 2009 por representantes de grandes projetos PHP. "Interoperabilidade" é a palavra-chave: fazer peças de projetos diferentes funcionarem juntas.

Recomendação, não lei

O PHP roda código que não segue nenhuma PSR (você vai ver isso daqui a pouco). As PSRs não fazem parte da linguagem; são acordos. Mas o ecossistema inteiro (Composer, Laravel, Symfony, as bibliotecas do Packagist) segue as principais, e quem trabalha em equipe também.

Existem dois tipos de PSR:

TipoO que defineExemplos
Regras de escritaComo escrever e organizar o códigoPSR-1, PSR-12 (estilo), PSR-4 (autoload)
InterfacesUm contrato (uma interface) que várias bibliotecas implementam, para serem trocáveisPSR-3 (log), PSR-7 (HTTP), PSR-11 (contêiner), PSR-15 (middleware), PSR-18 (cliente HTTP)

PSR-12: a formatação

A PSR-12 continua a PSR-1 e decide o resto: espaços, chaves, linhas em branco. É um documento longo; você não precisa decorá-lo, porque as ferramentas conferem e consertam sozinhas (próxima seção). Mas reconheça o formato:

<?php

declare(strict_types=1);

namespace Ana\Lojinha;

use InvalidArgumentException;

class Carrinho
{
    public const TAXA = 0.05;

    private array $itens = [];

    public function adicionarItem(string $nome, float $preco): void
    {
        if ($preco <= 0) {
            throw new InvalidArgumentException("Preço inválido: $preco");
        }

        $this->itens[$nome] = $preco;
    }

    public function calcularTotal(): float
    {
        $total = array_sum($this->itens);

        return $total > 100 ? $total : $total * (1 + self::TAXA);
    }
}

PSR-2, PSR-12 e PER Coding Style

Você vai encontrar três nomes. A PSR-2 foi a primeira regra de formatação (2012) e está obsoleta. A PSR-12 (2019) a substituiu. Como o PHP ganhou recursos depois disso (enums, match, atributos, property hooks), o PHP-FIG passou a manter o PER Coding Style (PER = "PHP Evolving Recommendation", recomendação que evolui), que estende a PSR-12 para a sintaxe nova. Na prática, quem segue a PSR-12 já segue quase tudo.

PSR-4: o autoload

Você já conhece: é a regra "prefixo de namespace → pasta base; o resto do nome vira subpastas; a classe vira Classe.php". Ana\Lojinha\Pagamento\Pix com o prefixo Ana\Lojinha\ em src/ fica em src/Pagamento/Pix.php. Veja os detalhes em Autoload e PSR-4. (A antiga PSR-0, que fazia algo parecido, está obsoleta.)

PSR-3: uma interface de log para todos

Na aula do Composer, a classe Pedido da Ana recebia um LoggerInterface, e não um Monolog\Logger. Essa interface vem do pacote psr/log, que é a PSR-3 em forma de código. Ela define os métodos que todo "registrador de log" deve ter:

MétodoPara quê
emergency()O sistema está fora do ar
alert()Alguém precisa agir já (ex.: banco de dados inacessível)
critical()Erro grave (ex.: exceção não esperada)
error()Erro que não para o sistema, mas deve ser investigado
warning()Algo estranho que não é erro (estoque baixo, recurso obsoleto)
notice()Evento normal, mas importante
info()Evento interessante (pedido fechado, usuário entrou)
debug()Detalhes para depurar
log($nivel, …)Registra em qualquer nível

Todos recebem (string|Stringable $message, array $context = []). A PSR-3 também combina que a mensagem pode ter marcadores entre chaves, como {cliente}, trocados pelos valores do $context.

Por que isso importa: trocar sem mexer

Como o Pedido depende só da interface, qualquer classe que a implemente serve. A Ana escreveu um logger caseiro, que só mostra na tela, estendendo a classe AbstractLogger do próprio psr/log (ela já implementa os oito métodos chamando o log(); basta escrever esse):

<?php

declare(strict_types=1);

namespace Ana\Lojinha;

use Psr\Log\AbstractLogger;
use Stringable;

class LoggerDeTela extends AbstractLogger
{
    public function log($level, string|Stringable $message, array $context = []): void
    {
        // troca {chave} pelo valor do contexto, como a PSR-3 sugere
        $trocas = [];
        foreach ($context as $chave => $valor) {
            $trocas['{' . $chave . '}'] = $valor;
        }
        echo strtoupper($level), ": ", strtr((string) $message, $trocas), "\n";
    }
}

PSR-7 e PSR-15: HTTP como objetos (só a ideia)

Até aqui, no guia, uma requisição web é lida pelas superglobais ($_GET, $_POST, $_SERVER) e a resposta é feita com echo e header(). Funciona, mas espalha a requisição por variáveis globais e deixa a resposta "já enviada" assim que o primeiro echo roda.

A PSR-7 define interfaces para representar a conversa HTTP como objetos:

Interface (PSR-7)RepresentaExemplos de métodos
ServerRequestInterfaceA requisição que chegougetMethod(), getQueryParams() (o $_GET), getParsedBody() (o $_POST), getHeaderLine('Accept')
ResponseInterfaceA resposta que vai sairwithStatus(404), withHeader('Content-Type', 'application/json'), getBody()
UriInterface, StreamInterface…O endereço, o corpogetPath(), write()

Um detalhe marcante: esses objetos são imutáveis. $resposta->withStatus(404) não muda a resposta; devolve uma cópia com o status novo (por isso o nome começa com with, "com").

A PSR-15 usa a PSR-7 para definir middlewares: "camadas" por onde a requisição passa antes de chegar à sua página (conferir login, registrar log, comprimir a resposta). Cada camada é uma classe com um único método:

<?php
// Só a forma da interface (do pacote psr/http-server-middleware):
interface MiddlewareInterface
{
    public function process(
        ServerRequestInterface $request,
        RequestHandlerInterface $handler
    ): ResponseInterface;
}
// Cada middleware recebe a requisição, faz o seu trabalho
// e chama $handler->handle($request) para passar adiante.

Como são interfaces padrão, um middleware de login escrito para um framework funciona em outro. Frameworks como Slim e Mezzio são construídos assim; o Laravel e o Symfony têm formatos próprios, mas sabem converter para PSR-7. Você não precisa usar nada disso agora: quando encontrar $request->getParsedBody() num tutorial, já sabe de onde veio.

Quando dá errado

"Funciona, mas o revisor recusou"

O que significa: o projeto exige PSR-12, e o seu código está fora do padrão. O PHP não reclama de estilo; a equipe, sim.

Como consertar: rode vendor/bin/phpcbf --standard=PSR12 src (ou o PHP-CS-Fixer) antes de enviar; depois confira com phpcs e conserte à mão os nomes.

must be of type Psr\Log\LoggerInterface, MeuLog given

O que significa: você passou um objeto que tem os métodos certos, mas a classe não declara a interface. Para o PHP, "parecer" não basta.

Como consertar: class MeuLog implements LoggerInterface (com todos os métodos) ou class MeuLog extends AbstractLogger (só o log()).

phpcs: "Class name … is not in PascalCase format" depois do phpcbf

O que significa: o conserto automático não muda nomes, porque trocar o nome de uma classe ou método quebraria todo código que os usa.

Como consertar: renomeie à mão, ou com a função "Renomear" do editor, que atualiza todos os usos de uma vez.

Resumo

  • PSRs são recomendações do PHP-FIG para padronizar o estilo e permitir que bibliotecas se encaixem. O PHP não as exige; o ecossistema, sim.
  • PSR-1: <?php, UTF-8, classes em PascalCase, métodos em camelCase, constantes em MAIÚSCULAS. PSR-12 (e o PER Coding Style): 4 espaços, chaves de classe/método na linha de baixo, de if na mesma linha, visibilidade sempre.
  • phpcs aponta, phpcbf e PHP-CS-Fixer consertam; nomes você troca à mão.
  • PSR-4: namespace → pasta (autoload).
  • PSR-3: LoggerInterface, com info(), warning(), error()… e marcadores {chave}. Dependa da interface, não da biblioteca.
  • PSR-7: requisição e resposta HTTP como objetos imutáveis; PSR-15: middlewares que usam esses objetos.
