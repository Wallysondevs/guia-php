PHP Testes com PHPUnit

Toda vez que a Ana muda o carrinho da lojinha, ela abre o site, coloca produtos, aplica um cupom e confere o total na calculadora. Funciona, mas cansa, e um dia ela vai esquecer de conferir alguma coisa. Um teste automatizado é um pequeno programa que faz essa conferência por ela, em segundos, quantas vezes ela quiser. O PHPUnit é a ferramenta padrão do PHP para escrever e rodar esses testes.

Você vai aprender
  • O que é um teste automatizado e por que ele vale o trabalho.
  • Instalar o PHPUnit com o Composer, só para o desenvolvimento.
  • Escrever uma classe de teste (TestCase) com assertSame.
  • Rodar com vendor/bin/phpunit e ler a saída de sucesso e de falha.
  • Testar exceções com expectException.
  • Testar vários casos de uma vez com data providers (#[DataProvider]).
  • Configurar o projeto com phpunit.xml e ver os testes como frases com --testdox.
O PHPUnit não roda no editor do guia. Ele é instalado pelo Composer, que precisa de internet e de um terminal de verdade. Todas as saídas de composer e vendor/bin/phpunit desta aula vieram do computador da Ana (PHPUnit 13.4.3, PHP 8.5). Nas caixas "Experimente", você vai treinar a mesma ideia com um "mini PHPUnit" de poucas linhas, escrito em PHP puro.

A ideia: a lista de conferência do confeiteiro

Um confeiteiro que muda a receita do bolo não serve o bolo novo direto ao cliente: ele prova. E um confeiteiro organizado tem uma lista do que provar: "está doce?", "a massa cresceu?", "o recheio não vazou?". Se mudar o fermento, ele passa a lista inteira de novo, porque às vezes mexer numa coisa estraga outra.

Um teste é um item dessa lista, escrito em PHP: "um carrinho novo tem 0 itens", "2 cadernos de R$ 25,50 dão R$ 51,00", "o cupom PROMO10 tira 10%". O PHPUnit passa a lista inteira e responde com um relatório. Quase todo teste segue três passos, conhecidos como Preparar, Agir, Conferir:

  1. Preparar: criar o que o teste precisa (um carrinho, uns produtos).
  2. Agir: chamar o método que está sendo testado.
  3. Conferir: comparar o resultado com o esperado (uma assertion, "afirmação").

Esta é a classe que vamos testar. Ela guarda os itens num array (produto → preço e quantidade), soma as quantidades, calcula o total e aplica cupons:

<?php

declare(strict_types=1);

namespace Loja;

use InvalidArgumentException;

final class Carrinho
{
    /** @var array<string, array{preco: float, quantidade: int}> */
    private array $itens = [];

    public function adicionar(string $produto, float $preco, int $quantidade = 1): void
    {
        if ($quantidade < 1) {
            throw new InvalidArgumentException("Quantidade inválida: $quantidade");
        }

        if (isset($this->itens[$produto])) {
            $this->itens[$produto]['quantidade'] += $quantidade;
        } else {
            $this->itens[$produto] = ['preco' => $preco, 'quantidade' => $quantidade];
        }
    }

    public function quantidadeDeItens(): int
    {
        return array_sum(array_column($this->itens, 'quantidade'));
    }

    public function total(): float
    {
        $total = 0.0;
        foreach ($this->itens as $item) {
            $total += $item['preco'] * $item['quantidade'];
        }
        return round($total, 2);
    }

    public function totalComCupom(string $cupom): float
    {
        $desconto = match ($cupom) {
            'PROMO10' => 0.10,
            'METADE'  => 0.50,
            ''        => 0.0,
            default   => throw new InvalidArgumentException("Cupom desconhecido: $cupom"),
        };
        return round($this->total() * (1 - $desconto), 2);
    }
}

3. O primeiro teste

<?php

declare(strict_types=1);

use Loja\Carrinho;
use PHPUnit\Framework\TestCase;

final class CarrinhoTest extends TestCase
{
    public function testCarrinhoNovoEstaVazio(): void
    {
        $carrinho = new Carrinho();

        $this->assertSame(0, $carrinho->quantidadeDeItens());
        $this->assertSame(0.0, $carrinho->total());
    }

    public function testTotalSomaPrecoVezesQuantidade(): void
    {
        $carrinho = new Carrinho();
        $carrinho->adicionar('Caderno', 25.50, 2);
        $carrinho->adicionar('Caneta', 3.90, 10);

        $this->assertSame(90.0, $carrinho->total());
    }
}
use PHPUnit\Framework\TestCase;
Importa a classe base dos testes (veja Namespaces).
final class CarrinhoTest extends TestCase
Uma classe de teste herda de TestCase. Por convenção, o nome é o da classe testada + Test, e o arquivo tem o mesmo nome: CarrinhoTest.php.
public function testCarrinhoNovoEstaVazio(): void
Cada método público cujo nome começa com test é um teste. O resto do nome descreve o que se confere, como uma frase.
$carrinho = new Carrinho();
Preparar. Cada teste cria o seu carrinho do zero: um teste nunca depende de outro.
$carrinho->adicionar(…)
Agir.
$this->assertSame(esperado, obtido)
Conferir. "Afirme que são idênticos": passa se esperado === obtido (mesmo valor e mesmo tipo). Primeiro o valor esperado, depois o obtido.

Quando um teste falha

A Ana acrescentou um teste para um caso que ela tinha medo de quebrar: adicionar o mesmo produto duas vezes deve somar as quantidades.

    public function testAdicionarOMesmoProdutoSomaAsQuantidades(): void
    {
        $carrinho = new Carrinho();
        $carrinho->adicionar('Caneta', 3.90, 2);
        $carrinho->adicionar('Caneta', 3.90, 3);

        $this->assertSame(5, $carrinho->quantidadeDeItens());

Para ver o que acontece numa falha, ela "quebrou" o carrinho de propósito, trocando += por = no adicionar (a segunda vez substitui a quantidade em vez de somar):

4. Testando exceções: expectException

Às vezes o comportamento certo é dar erro: adicionar 0 canetas deve lançar uma exceção. Para testar isso, avise o PHPUnit antes de agir:

    public function testQuantidadeZeroLancaExcecao(): void
    {
        $carrinho = new Carrinho();

        $this->expectException(InvalidArgumentException::class);
        $this->expectExceptionMessage('Quantidade inválida: 0');

        $carrinho->adicionar('Caneta', 3.90, 0);
    }

    public function testPrecoNegativoLancaExcecao(): void
    {
        $carrinho = new Carrinho();

        $this->expectException(InvalidArgumentException::class);

        $carrinho->adicionar('Caneta', -3.90);
    }
expectException(InvalidArgumentException::class)
"Espere uma exceção deste tipo." O teste passa se ela for lançada e falha se o código terminar normalmente. ::class dá o nome completo da classe como texto.
expectExceptionMessage('…')
Opcional: confere também se a mensagem contém esse texto.
a última linha
A ação que deve lançar a exceção vem depois do expect. O que estiver depois dela no método não roda (a exceção interrompe).

O primeiro passa: o Carrinho já recusa quantidade 0. E o segundo? O --filter roda só os testes cujo nome contém o texto dado:

$ vendor/bin/phpunit --filter testPrecoNegativo tests/CarrinhoTest.php

"Falhou ao afirmar que uma exceção do tipo InvalidArgumentException é lançada." O teste encontrou um defeito de verdade: o carrinho aceita preço negativo! A Ana acrescentou a validação no adicionar, logo depois da conferência da quantidade:

        if ($preco < 0) {
            throw new InvalidArgumentException("Preço inválido: $preco");
        }

Repare na ordem em que isso aconteceu: primeiro o teste (que falhou), depois o código (que fez o teste passar). Escrever o teste antes do código tem nome: TDD (Test-Driven Development, "desenvolvimento guiado por testes"). Não é obrigatório, mas é uma ótima forma de pensar no que o código deve fazer antes de fazê-lo.

5. Vários casos de uma vez: data providers

Para testar o cupom, a Ana quer conferir três situações: sem cupom, PROMO10 e METADE. Escrever três métodos quase iguais seria repetitivo. Um data provider ("fornecedor de dados") é um método que devolve uma lista de casos; o PHPUnit roda o mesmo teste uma vez para cada caso.

<?php

declare(strict_types=1);

use Loja\Carrinho;
use PHPUnit\Framework\Attributes\DataProvider;
use PHPUnit\Framework\TestCase;

final class CarrinhoTest extends TestCase
{
    // … os testes anteriores …

    #[DataProvider('cupons')]
    public function testTotalComCupom(string $cupom, float $esperado): void
    {
        $carrinho = new Carrinho();
        $carrinho->adicionar('Caderno', 25.50, 2);
        $carrinho->adicionar('Caneta', 3.90, 10);

        $this->assertSame($esperado, $carrinho->totalComCupom($cupom));
    }

    public static function cupons(): array
    {
        return [
            'sem cupom'       => ['', 90.0],
            'dez por cento'   => ['PROMO10', 81.0],
            'metade do preço' => ['METADE', 40.0],
        ];
    }
}
use PHPUnit\Framework\Attributes\DataProvider;
Importa o atributo DataProvider.
#[DataProvider('cupons')]
Diz: "os dados deste teste vêm do método cupons". Em versões antigas do PHPUnit, isso era um comentário @dataProvider; no PHPUnit 12 e 13, use o atributo.
testTotalComCupom(string $cupom, float $esperado)
O teste agora recebe parâmetros: um caso por vez.
public static function cupons(): array
O provider precisa ser public e static. Cada item é um caso: a chave é o nome do caso (aparece nos relatórios) e o valor é a lista de argumentos, na ordem dos parâmetros.

Repare no último caso: a Ana fez a conta de cabeça e escreveu 40,00 para o cupom METADE. Rodando só esse teste:

6. O phpunit.xml e o --testdox

Digitar tests/CarrinhoTest.php toda vez cansa, e um projeto real tem dezenas de arquivos de teste. Um arquivo phpunit.xml na raiz do projeto diz ao PHPUnit onde procurar:

<?xml version="1.0" encoding="UTF-8"?>
<phpunit xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:noNamespaceSchemaLocation="vendor/phpunit/phpunit/phpunit.xsd"
         bootstrap="vendor/autoload.php"
         colors="true">
    <testsuites>
        <testsuite name="lojinha">
            <directory>tests</directory>
        </testsuite>
    </testsuites>
</phpunit>
bootstrap="vendor/autoload.php"
Carrega o autoload do Composer antes dos testes (é o que faz new Carrinho() encontrar src/Carrinho.php).
colors="true"
Verde para sucesso, vermelho para falha.
<directory>tests</directory>
Roda todos os arquivos *Test.php da pasta tests.

Agora basta vendor/bin/phpunit. E com --testdox, o PHPUnit transforma os nomes dos métodos em frases, uma lista de conferência legível até por quem não programa:

As assertions mais usadas

AssertionPassa quando…
assertSame($esperado, $obtido)$esperado === $obtido. A que você mais vai usar.
assertEquals($esperado, $obtido)$esperado == $obtido (aceita tipos diferentes: 51 e 51.0).
assertEqualsWithDelta(0.3, $obtido, 0.0001)A diferença é menor que a margem. Para contas com float (0.1 + 0.2 não é exatamente 0.3).
assertTrue($x) / assertFalse($x)$x === true / $x === false.
assertNull($x)$x === null.
assertCount(3, $lista)A lista tem 3 elementos.
assertContains('Caneta', $lista)O valor está na lista.
assertArrayHasKey('preco', $item)O array tem a chave.
assertStringContainsString('R$', $texto)O texto contém o pedaço.
assertInstanceOf(Carrinho::class, $obj)O objeto é daquela classe.
expectException(Classe::class)(Antes da ação.) A ação lança essa exceção.

Formas diferentes de organizar

  • Um teste, uma ideia. Prefira vários testes pequenos com nomes claros a um teste gigante: quando falhar, o nome já diz o que quebrou.
  • setUp(): um método protected function setUp(): void roda antes de cada teste. Use para a preparação repetida (por exemplo, $this->carrinho = new Carrinho();, guardado numa propriedade).
  • Data provider quando o teste é o mesmo e só mudam os dados (como os cupons).
  • O que testar: o caso comum, os limites (0, 1, vazio, o maior valor permitido) e os erros esperados (exceções). Não precisa testar o PHP (que array_sum soma, por exemplo); teste as suas regras.

Você viu esse acima. O que significa: o teste esperava uma exceção (expectException) e o código terminou sem lançar nenhuma. Ou o código não valida aquele caso (foi o preço negativo), ou a ação veio antes do expectException no método.

Como consertar: confira a ordem (expect… primeiro, ação por último) e, se a ordem estiver certa, implemente a validação que falta.

final class Carrinho
{

    public function adicionar(string $produto, float $preco, int $quantidade = 1): void

        }

    {

Resumo

  • Um teste automatizado confere o seu código por você: Preparar, Agir, Conferir.
  • Instale com composer require --dev phpunit/phpunit e rode com vendor/bin/phpunit.
  • Classe XTest extends TestCase; métodos públicos começando com test; $this->assertSame($esperado, $obtido).
  • Saída: . passou, F falhou, E erro; OK (…) ou FAILURES!, com o nome do teste, a diferença e a linha.
  • expectException antes da ação para testar erros esperados; #[DataProvider] + método public static para vários casos.
  • phpunit.xml para rodar tudo com um comando; --testdox para ler os testes como frases; --filter para rodar só alguns.
  • Quando um teste falha, pode ser o código ou o teste que está errado: o PHPUnit só compara, a decisão é sua.
