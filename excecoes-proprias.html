PHP Criar suas Exceções

Na aula anterior, a lojinha da Ana lançava new Exception("Estoque insuficiente…"). Funciona, mas quem captura só tem a mensagem para saber o que aconteceu, e não dá para tratar "estoque acabou" de um jeito e "cartão recusado" de outro. A solução é criar tipos de exceção próprios, com nomes que dizem o problema. São classes de uma ou poucas linhas, e são a porta de entrada mais suave para a orientação a objetos.

Você vai aprender
  • Criar uma exceção com class EstoqueInsuficienteException extends Exception {}.
  • Capturar só o seu tipo, deixando os outros passarem.
  • Dar um construtor à exceção, com a mensagem pronta e dados extras (parent::__construct).
  • Montar uma hierarquia: uma exceção "mãe" da loja e várias "filhas".
  • Estender as exceções prontas do PHP (InvalidArgumentException…).
  • Quando vale a pena criar uma exceção, e quando não.

Você precisa ter visto Exceções (try e catch). Esta aula usa duas ideias de orientação a objetos, explicadas aqui só o suficiente: classe (um "molde" de objetos) e herança (extends, "estende": uma classe nova que aproveita tudo de outra). Elas são estudadas a fundo em Classes e Objetos e Herança, no Nível 3.

A ideia: etiquetas nos avisos

Imagine que todos os avisos da cozinha fossem papeizinhos brancos com um texto. Para saber se é "acabou o ovo" ou "o forno quebrou", você precisa ler cada um. Agora imagine papeizinhos coloridos: amarelo é falta de ingrediente, vermelho é equipamento quebrado. Você separa só de olhar, e cada cor vai para a pessoa certa. Criar uma exceção própria é criar uma nova "cor" de aviso.

A exceção mais simples

<?php
class EstoqueInsuficienteException extends Exception
{
}

function vender(string $produto, int $estoque, int $quantidade): int
{
    if ($quantidade > $estoque) {
        throw new EstoqueInsuficienteException("Só há $estoque de $produto");
    }
    return $estoque - $quantidade;
}

try {
    vender('bolo de cenoura', 2, 5);
} catch (EstoqueInsuficienteException $e) {
    echo "Avise o cliente: ", $e->getMessage(), "\n";
}
vender('torta', 1, 3);

Um construtor: mensagem pronta e dados extras

Com a classe vazia, cada throw precisa montar a mensagem, e quem captura só recebe texto. Se o catch quiser saber quantos faltaram, teria que "ler" a mensagem. Melhor: a exceção guarda os dados e monta a mensagem sozinha. Para isso ela ganha um construtor (__construct), a função que roda quando você escreve new:

<?php
class EstoqueInsuficienteException extends Exception
{
    public function __construct(
        public readonly string $produto,
        public readonly int $pedido,
        public readonly int $disponivel,
    ) {
        parent::__construct("Estoque insuficiente de $produto: pediu $pedido, há $disponivel");
    }
}

try {
    throw new EstoqueInsuficienteException('brigadeiro', 50, 30);
} catch (EstoqueInsuficienteException $e) {
    echo $e->getMessage(), "\n";
    echo "Falta(m) ", $e->pedido - $e->disponivel, " {$e->produto}(s)\n";
    echo "Linha: ", $e->getLine(), "\n";
}
TrechoO que faz
public function __construct(…)O construtor: recebe os valores passados em new EstoqueInsuficienteException('brigadeiro', 50, 30). Veja Construtores.
public readonly string $produto,Recebe o parâmetro e já cria uma propriedade $produto com o valor (a "promoção de construtor", PHP 8.0+). public: dá para ler de fora ($e->produto). readonly (8.1+): ninguém pode mudar depois.
parent::__construct("…")Chama o construtor da classe mãe (Exception) com a mensagem montada. É ele que guarda a mensagem para o getMessage(). Não esqueça esta linha!
$e->pedido - $e->disponivelQuem captura usa os dados, sem precisar interpretar o texto.
$ php construtor.php
Estoque insuficiente de brigadeiro: pediu 50, há 30
Falta(m) 20 brigadeiro(s)
Linha: 14                     « getLine continua funcionando: herdado da Exception

Agora o throw ficou curto e sem chance de mensagem mal escrita: throw new EstoqueInsuficienteException($produto, $qtd, $estoque);.

Uma família de exceções

A lojinha tem vários problemas possíveis: produto que não existe, estoque insuficiente, pagamento recusado. Cada um merece um tipo. E todos são "problemas da loja", então podem ter uma mãe comum:

<?php
class LojaException extends Exception {}
class EstoqueInsuficienteException extends LojaException {}
class ProdutoNaoEncontradoException extends LojaException {}
class PagamentoRecusadoException extends LojaException {}

$catalogo = ['bolo' => 2, 'torta' => 0];

function comprar(array $catalogo, string $produto, int $qtd, bool $cartaoOk): string
{
    if (!array_key_exists($produto, $catalogo)) {
        throw new ProdutoNaoEncontradoException("Não vendemos $produto");
    }
    if ($catalogo[$produto] < $qtd) {
        throw new EstoqueInsuficienteException("Só temos {$catalogo[$produto]} $produto(s)");
    }
    if (!$cartaoOk) {
        throw new PagamentoRecusadoException('Cartão recusado');
    }
    return "Compra de $qtd $produto(s) aprovada";
}

$tentativas = [['bolo', 1, true], ['pastel', 1, true], ['torta', 1, true], ['bolo', 2, false]];
foreach ($tentativas as [$p, $q, $ok]) {
    try {
        echo comprar($catalogo, $p, $q, $ok), "\n";
    } catch (PagamentoRecusadoException $e) {
        echo "Pagamento: ", $e->getMessage(), " (tente outro cartão)\n";
    } catch (LojaException $e) {
        echo get_class($e), ": ", $e->getMessage(), "\n";
    }
}
var_dump(new EstoqueInsuficienteException() instanceof LojaException);
var_dump(new EstoqueInsuficienteException() instanceof Exception);
print_r(class_parents(new EstoqueInsuficienteException()));

A árvore fica assim:

Throwable
└── Exception
    └── LojaException
        ├── EstoqueInsuficienteException
        ├── ProdutoNaoEncontradoException
        └── PagamentoRecusadoException

(

)

Com a família, quem captura escolhe o nível de detalhe:

  • catch (PagamentoRecusadoException $e): só aquele problema, com tratamento especial.
  • catch (LojaException $e): qualquer problema da loja, de uma vez. Se amanhã surgir uma CupomInvalidoException extends LojaException, esse catch já a pega, sem mudar nada.
  • Problemas que não são da loja (um TypeError, um JsonException) passam reto e não são confundidos com regras de negócio.

Estender as exceções do PHP

A sua exceção não precisa ser filha direta de Exception. Se ela é um caso particular de uma exceção que o PHP já tem (veja a tabela na aula anterior), estenda essa:

<?php
class QuantidadeInvalidaException extends InvalidArgumentException {}

function quantidade(string $texto): int
{
    if (!ctype_digit($texto)) {
        throw new QuantidadeInvalidaException("Quantidade inválida: '$texto'");
    }
    return (int) $texto;
}
try {
    quantidade('dez');
} catch (InvalidArgumentException $e) {
    echo get_class($e), " pega como InvalidArgumentException: ", $e->getMessage(), "\n";
}

$ php spl.php
QuantidadeInvalidaException pega como InvalidArgumentException: Quantidade inválida: 'dez'

Assim, um código que já captura InvalidArgumentException (de uma biblioteca, por exemplo) continua funcionando com a sua exceção.

E extends Error?

Não faça. A família Error é para erros internos do PHP (tipo errado, função inexistente). As suas exceções são da família Exception.

Organizar em arquivos

Num sistema de verdade, as exceções ficam num arquivo próprio (ou um arquivo por classe), carregado com require_once (aula include e require):

<?php
class LojaException extends Exception {}

class EstoqueInsuficienteException extends LojaException
{
    public function __construct(
        public readonly string $produto,
        public readonly int $pedido,
        public readonly int $disponivel,
    ) {
        parent::__construct("Estoque insuficiente de $produto: pediu $pedido, há $disponivel");
    }
}

<?php
require_once __DIR__ . '/excecoes.php';

try {
    throw new EstoqueInsuficienteException('pudim', 3, 1);
} catch (LojaException $e) {
    echo $e->getMessage(), "\n";
}

$ php usa-arquivo.php
Estoque insuficiente de pudim: pediu 3, há 1

No Nível 3 você vai ver o padrão profissional: cada classe no seu arquivo (EstoqueInsuficienteException.php), em namespaces, carregadas pelo autoload sem nenhum require.

Quando criar uma exceção própria?

SituaçãoFaça
Quem chama vai querer tratar esse problema de um jeito diferente dos outrosCrie uma exceção própria (PagamentoRecusadoException)
O problema tem dados úteis para quem trata (quanto faltou, qual produto)Exceção própria com construtor e propriedades
Seu sistema (ou biblioteca) tem vários problemas "de negócio"Uma mãe comum (LojaException) e filhas
Um argumento inválido qualquer, que ninguém vai tratar de forma especialUse a pronta: InvalidArgumentException
"Não encontrei" é um resultado normal (buscar um cliente que pode não existir)Nem exceção: devolva null
Uma exceção para cada linha do programaNão: exceções demais viram ruído. Crie quando o tipo fizer diferença para quem captura.

Resumo

  • Uma exceção própria é uma classe que estende Exception: class EstoqueInsuficienteException extends Exception {}.
  • O nome diz o problema e termina em Exception; quem captura pode tratá-la separadamente.
  • Um construtor guarda dados (public readonly) e monta a mensagem, entregue com parent::__construct(…).
  • Uma mãe comum (LojaException) permite capturar a família toda; filhas permitem tratar casos específicos.
  • Casos particulares de exceções do PHP podem estendê-las (extends InvalidArgumentException); nunca estenda Error.
  • Crie exceções quando o tipo fizer diferença para quem captura.
