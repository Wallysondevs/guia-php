PHP Upload de Arquivos

Foto de perfil, currículo em PDF, comprovante de pagamento: muitos sites recebem arquivos. Em PHP, isso usa o mesmo formulário que você já conhece, com dois detalhes a mais, e uma superglobal nova, $_FILES. Receber é fácil; o cuidado está em conferir o que chegou, porque um arquivo enviado por um desconhecido é a coisa mais perigosa que um site pode guardar.

Você vai aprender
  • O formulário de upload: method="post", enctype="multipart/form-data" e <input type="file">.
  • A estrutura de $_FILES, vista com var_dump: name, type, tmp_name, error, size.
  • Como guardar o arquivo com move_uploaded_file.
  • Por que não confiar na extensão nem no type, e como descobrir o tipo de verdade com finfo.
  • Os limites de tamanho: upload_max_filesize, post_max_size e MAX_FILE_SIZE.
  • Os códigos de erro UPLOAD_ERR_*.
  • Como dar ao arquivo um nome seguro.

A ideia: a encomenda que chega na portaria

Quando chega um pacote no prédio da Ana, o porteiro não leva direto para o apartamento. Ele guarda numa sala de espera e anota numa ficha: nome escrito na etiqueta, tamanho, se chegou inteiro. A Ana então decide: abre a caixa, confere se é mesmo o que encomendou e leva para casa. Se não buscar, o pacote é descartado.

O upload no PHP é igualzinho:

  • O PHP recebe o arquivo e o guarda numa pasta temporária (a sala de espera), com um nome aleatório.
  • Ele preenche uma ficha em $_FILES: nome original, tamanho, tipo informado, se houve erro.
  • O seu programa confere e, se estiver tudo certo, move o arquivo para uma pasta definitiva. Se não mover, o PHP apaga o temporário assim que a página termina.

E, como na portaria, a etiqueta do pacote pode mentir: o nome e o tipo informados foram escritos por quem enviou.

O formulário de upload

<form action="upload.php" method="post" enctype="multipart/form-data">
  <p>Foto: <input type="file" name="foto" accept="image/*"></p>
  <p>Legenda: <input name="legenda"></p>
  <button>Enviar</button>
</form>
method="post"
Obrigatório. Arquivos não cabem no endereço (GET).
enctype="multipart/form-data"
Encoding type, "tipo de codificação". O formato normal (nome=valor&…, de Formulários HTML) só leva texto. O multipart/form-data divide o pedido em "partes" separadas, e cada parte pode ser um campo de texto ou um arquivo inteiro. Sem isso, o arquivo não vai.
<input type="file" name="foto">
O botão "Escolher arquivo". O name é a chave em $_FILES.
accept="image/*"
Sugere ao navegador mostrar só imagens na janela de escolha. É conforto, não proteção: a pessoa pode trocar para "todos os arquivos".
name="legenda"
Campos de texto continuam funcionando normalmente, e chegam em $_POST.

Guardar: move_uploaded_file

Para tirar o arquivo da sala de espera, use move_uploaded_file ("mover arquivo enviado"):

<?php
$arq = $_FILES['foto'];
$destino = 'uploads/' . $arq['name'];
if (move_uploaded_file($arq['tmp_name'], $destino)) {
    echo "Salvo em $destino\n";
} else {
    echo "Não foi possível salvar.\n";
}
move_uploaded_file(
Move o arquivo e devolve true (deu certo) ou false.
$arq['tmp_name'],
De onde: o arquivo temporário. A função só aceita arquivos que chegaram por upload neste pedido; um caminho qualquer, como /etc/passwd, é recusado. Por isso use ela, e não rename ou copy.
$destino)
Para onde: o caminho final, com o nome do arquivo. A pasta precisa existir e o PHP precisa ter permissão de escrita nela.

Três configurações controlam o tamanho, e é bom conhecer as três porque cada uma falha de um jeito:

Para o seu programa, parece que o formulário veio vazio. Se REQUEST_METHOD é POST mas $_POST e $_FILES estão vazios, desconfie do post_max_size.

O campo MAX_FILE_SIZE vai antes do <input type="file">:

Para aceitar arquivos maiores, aumente os dois no php.ini (com post_max_size um pouco maior que upload_max_filesize, porque o pedido também leva os outros campos), ou, no servidor de testes, na linha de comando:

$ php -d upload_max_filesize=10M -d post_max_size=12M -S localhost:8000

E, no seu código, tenha o seu limite ($arq['size'] > 1_000_000), que não depende da configuração do servidor.

Validar o tipo: não confie na extensão

Uma foto chamada gato.jpg é uma foto? Não necessariamente. O nome (e a extensão .jpg) e o type (image/jpeg) foram escritos por quem enviou. A Ana copiou um arquivo de texto com o nome falsa.jpg e mandou com o curl dizendo que era JPEG:

<?php
$arq = $_FILES['foto'];
echo "O navegador disse: ", $arq['type'], "\n";
$finfo = new finfo(FILEINFO_MIME_TYPE);
echo "O finfo viu:       ", $finfo->file($arq['tmp_name']), "\n";
echo "mime_content_type: ", mime_content_type($arq['tmp_name']), "\n";

$ curl -s localhost:8000/tipo.php -F "foto=@falsa.jpg;type=image/jpeg"
O navegador disse: image/jpeg      « a etiqueta mentiu
O finfo viu:       text/plain      « o conteúdo é texto
mime_content_type: text/plain
$ curl -s localhost:8000/tipo.php -F "foto=@bolo.jpg"
O navegador disse: image/jpeg
O finfo viu:       image/jpeg
mime_content_type: image/jpeg
new finfo(FILEINFO_MIME_TYPE)
Cria um "inspetor de arquivos" (file info) da extensão fileinfo. Ele abre o arquivo e olha os primeiros bytes, a "assinatura" que todo formato tem (um PNG sempre começa com os bytes ‰PNG, um JPEG com FF D8 FF). FILEINFO_MIME_TYPE pede a resposta no formato tipo/subtipo.
$finfo->file($caminho)
Devolve o tipo descoberto pelo conteúdo. (A seta -> chama um método de um objeto, assunto de Classes e Objetos; aqui, basta copiar a forma.)
mime_content_type($caminho)
Faz o mesmo numa função só. Use a que achar mais simples.

Por que isso importa? O pior caso é alguém enviar um programa PHP com nome de foto. Se ele for salvo numa pasta acessível pelo navegador com a extensão .php, o atacante abre o endereço e o servidor executa o programa dele. O finfo não se engana com o nome:

$ php tipos.php
falsa.jpg: text/plain
foto.png: image/png
script.jpg: text/x-php            « um programa PHP disfarçado de .jpg

A defesa tem duas partes, e as duas são necessárias:

  1. Aceitar só os tipos que você espera, descobertos pelo finfo, numa lista (['image/jpeg' => 'jpg', 'image/png' => 'png']).
  2. Escolher a extensão do arquivo salvo a partir dessa lista, nunca a partir do nome original. Assim, mesmo um arquivo malicioso nunca é salvo como .php.

Nomes seguros

Usar $arq['name'] como nome do arquivo salvo traz vários problemas:

  • Sobrescrever: duas pessoas enviam foto.jpg, e a segunda apaga a primeira.
  • Extensões perigosas: foto.php, .htaccess.
  • Caracteres problemáticos: espaços, acentos, parênteses (minha foto (1).PNG), nomes enormes.
  • Caminhos: um nome como ../../index.php tentaria sair da pasta. O PHP já corta o caminho do name (fica só index.php), mas o full_path mantém tudo:
$ curl -s localhost:8000/dump.php -F "foto=@receita.txt;filename=../../index.php"
array(1) {
  ["foto"]=>
  array(6) {
    ["name"]=>
    string(9) "index.php"
    ["full_path"]=>
    string(15) "../../index.php"
…

A solução é inventar o nome: letras aleatórias + a extensão da sua lista. random_bytes(16) gera 16 bytes aleatórios, e bin2hex os escreve como 32 letras e números (0-9, a-f):

$novoNome = bin2hex(random_bytes(16)) . '.' . $tipos[$tipo];
// por exemplo: 1a99be15d05c6e4708f3bc45fd5c9c9b.png

Se precisar mostrar o nome original depois ("gato.png"), guarde-o num banco de dados junto do nome novo, e mostre-o com htmlspecialchars (Escapar a Saída).

Tudo junto: o upload seguro

<?php
$mensagem = '';

if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    $arq = $_FILES['foto'] ?? null;
    $tipos = ['image/jpeg' => 'jpg', 'image/png' => 'png', 'image/webp' => 'webp'];

    if ($arq === null || !is_int($arq['error'])) {
        $mensagem = 'Nenhum arquivo recebido.';
    } elseif ($arq['error'] === UPLOAD_ERR_NO_FILE) {
        $mensagem = 'Escolha uma foto.';
    } elseif ($arq['error'] === UPLOAD_ERR_INI_SIZE || $arq['error'] === UPLOAD_ERR_FORM_SIZE) {
        $mensagem = 'A foto é grande demais.';
    } elseif ($arq['error'] !== UPLOAD_ERR_OK) {
        $mensagem = 'O envio falhou (código ' . $arq['error'] . ').';
    } elseif ($arq['size'] > 1_000_000) {
        $mensagem = 'A foto pode ter no máximo 1 MB.';
    } else {
        $finfo = new finfo(FILEINFO_MIME_TYPE);
        $tipo = $finfo->file($arq['tmp_name']);
        if (!isset($tipos[$tipo])) {
            $mensagem = 'Envie uma imagem JPG, PNG ou WebP.';
        } else {
            $novoNome = bin2hex(random_bytes(16)) . '.' . $tipos[$tipo];
            if (move_uploaded_file($arq['tmp_name'], __DIR__ . '/uploads/' . $novoNome)) {
                $mensagem = 'Foto salva como ' . $novoNome;
            } else {
                $mensagem = 'Não foi possível salvar a foto.';
            }
        }
    }
}
?>

!is_int($arq['error'])Se alguém mandou foto[], o error vira array. Recuse.

Quando dá errado

$_FILES vazio, e o nome do arquivo apareceu em $_POST 
$ curl -s localhost:8000/dump.php -d "foto=gato.png"
array(0) {
}
array(1) {
  ["foto"]=>
  string(8) "gato.png"
}

O que aconteceu: o formulário não tem enctype="multipart/form-data". Sem ele, o navegador manda só o nome do arquivo, como texto comum (é o que o curl -d simula aqui), e o conteúdo fica para trás.

Como resolver: <form method="post" enctype="multipart/form-data">. Com method="get" também não funciona.

PHP Request Startup: POST Content-Length of … bytes exceeds the limit 
<b>Warning</b>:  PHP Request Startup: POST Content-Length of 9000317 bytes exceeds the limit of 8388608 bytes in <b>Unknown</b> on line <b>0</b><br />

O que aconteceu: o pedido inteiro passou do post_max_size (8388608 bytes = 8 MB). O PHP jogou fora $_POST e $_FILES.

Como resolver: aumente post_max_size (e upload_max_filesize) no php.ini, ou avise o limite no formulário. No código, trate "POST com $_FILES vazio" como "arquivo grande demais".

move_uploaded_file(…): Failed to open stream: No such file or directory

O que aconteceu: a pasta de destino não existe (ou o caminho está errado). A mensagem seguinte, Unable to move "/tmp/php…" to "uploads/…", é a consequência.

Como resolver: crie a pasta (mkdir uploads) e use caminho absoluto: __DIR__ . '/uploads/'. Se a mensagem for Permission denied, o PHP não tem permissão de escrita na pasta (no Linux, confira o dono e as permissões da pasta com ls -ld uploads).

O upload "deu certo", mas o arquivo sumiu

O que aconteceu: o código leu $_FILES mas não chamou move_uploaded_file (ou chamou com o destino errado e não conferiu o retorno). O arquivo temporário é apagado quando a página termina.

Como resolver: mova sempre, e confira: if (!move_uploaded_file(…)) { … }.

error 1 com um arquivo de 3 MB

O que aconteceu: o padrão de upload_max_filesize é 2M. Fotos de celular passam disso com facilidade.

Como resolver: aumente no php.ini (e o post_max_size junto), ou reduza a foto antes de enviar. Confira o valor em uso com php -i | grep upload_max_filesize ou ini_get('upload_max_filesize').

Missão: o finfo já descobriu que o arquivo é image/png. Monte em $novo um nome seguro: 32 caracteres aleatórios (bin2hex(random_bytes(16))), um ponto e a extensão que a lista $tipos dá para esse tipo. Ignore o nome original. A saída deve ser algo como 3f9a…c1.png.

<?php
$tipos = ['image/jpeg' => 'jpg', 'image/png' => 'png'];
$nomeOriginal = '../../minha foto (1).PHP';
$tipo = 'image/png';   // o que o finfo detectou

$novo = $nomeOriginal;   // troque por um nome seguro

echo $novo, "\n";

$tipos = ['image/jpeg' => 'jpg', 'image/png' => 'png'];

Resumo

  • Upload precisa de method="post", enctype="multipart/form-data" e <input type="file" name="…">.
  • $_FILES['campo'] traz name, full_path, type, tmp_name, error e size. Nome e tipo foram escritos por quem enviou.
  • Confira error (UPLOAD_ERR_OK = 0) antes de tudo; 4 = nenhum arquivo, 1 e 2 = grande demais.
  • Limites: upload_max_filesize (2M) por arquivo; post_max_size (8M) para o pedido inteiro, que, se estourar, esvazia $_POST e $_FILES.
  • Descubra o tipo pelo conteúdo, com finfo ou mime_content_type, e aceite só uma lista de tipos.
  • Salve com move_uploaded_file, com um nome inventado (bin2hex(random_bytes(16))) e a extensão da sua lista.
